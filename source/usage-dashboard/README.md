# 3DSRP private usage dashboard

Maintained by AuroraStudios84 · maintainer@example.invalid.

A read-only Cloudflare Worker sharing the existing `3dsrp-usage` D1 database.
It shows reporting installations, streamed time, sessions, average time per
installation, daily charts, searchable installation IDs, activity by installation
and day, and CSV export. Date presets cover 7, 30 and 90 days; custom ranges are
supported within the retained history. There are no external scripts, fonts,
tracking libraries or account tokens. The app selector covers All apps, New 3DS
and Original 3DS Relay, including details and CSV.

## Private access

Production requires Cloudflare Access on **3dsrp-dashboard only**, with all traffic
protected. In Workers & Pages, select that Worker → Access → Protect this Worker
behind Access → All traffic → Cloudflare account → Apply Access. Initial Zero
Trust setup may be required; choose the Free plan. Alternatively configure an
Access allow policy for the maintainer's exact email. Do not protect the ingestion
Worker (`3dsrp-usage`) or all Workers at account level: consoles cannot sign in.

The Worker independently requires the validated runtime `ctx.access` identity to
match `ALLOWED_EMAIL`. It never trusts caller-supplied email headers. Without
Access, or when signed in as another email, it returns 403 before any database
query or asset response. `access.dev` in wrangler.jsonc simulates identity only for
local development; it grants no production access. Previews are disabled.

HTML, CSS, JavaScript and the icon are embedded by `build.mjs`. This avoids the
Static Assets router, which does not forward `ctx.access` to the user Worker.
All responses are private/no-store, with a restrictive Content Security Policy.
The API only accepts GET/HEAD and exposes fixed, parameterized SELECT queries.
There are no write, arbitrary-SQL, or deletion endpoints. Worker logs and traces
are disabled. Access itself handles administrator sign-in.

## Development and deployment

Requires Node 22 or later and a Cloudflare account authorized to deploy Workers
and read the existing D1 database. From this directory:

```sh
npm ci
npm test
npm run dev
npm run deploy
```

The build runs automatically before each command. Configure the D1 binding and
allowed email in wrangler.jsonc for another account. Cloudflare credentials stay
in Wrangler's external configuration, never in this source tree. Existing deployments must apply the additive `../usage-service/schema-relay.sql`
migration before deploying this dashboard. Native tables/history remain unchanged. Local dev uses a separate local database; initialize it with the
schema at `../usage-service/schema.sql`. Never seed example data remotely.

## Interpretation and limits

The UUID identifies a reporting installation, not a person or an exact download
count. Only users who opt in and successfully upload appear. Activity dates come
from the console; recovered sessions keep their original dates. A session that
crosses midnight counts once on its earliest reported day, while duration is
split by activity day. First/last activity in the table refer to the selected
period. Average time uses installation-linked seconds divided by distinct app/ID pairs. A UUID shared across app families is two app
installations. Legacy ingestion clients remain classified as New 3DS.
Anonymous daily totals may include historical legacy reports without a UUID.
Installation history follows the existing 90-day retention policy.

Refresh is manual to keep reads low. Search and sorting apply to the installation
table and CSV, while overview cards/chart cover all activity for the selected
app and dates. Tables are paginated (25 rows by default); CSV supports up to 5,000 matching
installations and asks for narrower filters above that limit. Dashboard traffic
uses the account's shared Workers/D1 allowances; it adds no scheduled jobs or
paid services. No IP address collection is added.

## Verification

`npm test` covers private access, forged headers, other accounts, summary totals,
activity dates, midnight continuations, search, pagination, CSV, invalid filters,
read-only methods and safe errors. The local browser QA script at
`../../tools/dashboard-tests/browser.mjs` exercises desktop/mobile layout,
charts, dates, search, details, CSV, empty states and errors against synthetic
local-only data generated by `seed.mjs`. The browser executable in that script
is specific to the maintainer's build environment.
